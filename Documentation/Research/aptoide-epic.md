## Build facts

### Aptoide

- Console and docs: Aptoide Connect (Catappult was renamed Aptoide Connect in December 2024). docs.catappult.io now redirects (301) to docs.connect.aptoide.com; catappult.io/developers-distribution-policy redirects to connect.aptoide.com. Console languages: English and Japanese. New versions can also be sent through the Android App Version Submission API.
- Submission paths: (a) on Google Play with IAP: metadata imported, Android Billing SDK and PSV files required, subscription required; (b) on Google Play without IAP: free, Aptoide fetches the app files from Google Play and syncs Google Play updates within 24 hours (no Aptoide-specific build); (c) not on Google Play or under another package name: manual metadata and file upload, subscription required, package name likely needs Android Developer Verification registration.
- Package format: signed .apk only, up to 4 GB; .obb up to 5 GB; no .aab, .apks or zip. Files can be uploaded directly or given as public direct URLs. An AAB is turned into a standalone APK with bundletool build-apks --mode=universal --ks --ks-pass --ks-key-alias --key-pass.
- Minimum and target API: no store minimum published; "Target SDK < 16" is rejected. Aptoide Billing SDK: minSdk 21, compiled against target 33, Gradle plugin 8.6, build tools 8.4.0. No 64-bit or 16 KB page size rule found.
- Signing: APK must be signed; for a game on Google Play it must carry the Google Play certificate (Play App Signing: "Signed, universal APK" from an Internal testing release, then discard the draft and delete the bundle). A different signature triggers a Google Play Protect pop-up. Register the package and SHA-256 key in Android Developer Verification.
- Version code: higher than Google Play, unique per upload; a lower code than the installed version makes Android refuse the install (downgrade).
- Billing (required for any IAP): Aptoide Billing SDK, Maven com.aptoide:android-aptoide-billing:1.+ (repositories google, mavenCentral, jitpack). Unity: UPM git URL https://github.com/Aptoide/aptoide-unity-billing-sdk.git, Unity newer than 2022.2, JDK 11 wrapper, mainTemplate.gradle pins com.aptoide:android-aptoide-billing:1.5.0 and org.json:json:20210307, entry point AptoideBillingSDKManager.InitializePlugin(listeners, public key, gameObject.name). Payment runs through the Aptoide Wallet if installed, otherwise WebView payments or a prompt to install the wallet. Supports consumables, non-consumables, subscriptions (with free trials; obfuscatedAccountId required for trials), server Consume and Acknowledge APIs, RTDN. Legacy options: AppCoins SDK io.catappult:android-appcoins-billing (migrate by renaming packages to com.aptoide) and OSP (One-Step Payment), both covered only by migration guides; no end-of-support date published. Error 1429 means rate limiting (use exponential backoff).
- Revenue share: developer keeps 75% of net sales on Aptoide and partner stores (up to 93% with Revenue Boost), 90% for direct-to-consumer downloads.
- Ads: no Aptoide ad SDK required; invasive adware is rejected.
- Login: none required. Optional "Sign in to Aptoide Services" (restores non-consumables). Review tests account creation and every login method present.
- Cloud saves and game services: none documented.
- Review prompt: none; Aptoide states there is no equivalent of the Google Play In-App Review API. In-app updates and referral deeplinks exist through the Aptoide SDK (Android only).
- Forbidden SDKs: none listed by name. Google Play Billing is replaced; Play Integrity installer check must be off; external APK downloading is rejected.
- Permissions and APIs: permissions must be disclosed accurately. Policy Declarations (only for apps enabled for Aptoide Games in the US through Google Play) read the merged manifest of the latest version: AD_ID, health permissions (ACTIVITY_RECOGNITION, BODY_SENSORS, Health Connect); a permission change after completion sets the status to "Needs reconfirmation". The same card asks for test credentials when login, purchase or PIN restricts access.
- Review: manual QA by the admin team, typically 7 to 10 business days (contact support after 14). Checks: stability, device compatibility, core functionality and login, billing end to end, listing accuracy, content guidelines. Release can be scheduled, manual or automatic after approval.
- Trusted badge and malware: Aptoide Terms section 9.4 says the "Trusted App" sign only reflects automatic anti-virus and anti-malware tools used on selected content. The Distribution Policy (section 10.2(f)) lets Aptoide remove apps it deems malware; repeat malware uploads can terminate the account (10.7).
- Distribution: Aptoide and partner app stores, OEMs and carriers, chosen per channel on the first submission or under Configuration; each channel decides whether to list the app; some sync every 24 hours. The channel page names no partners, but the Aptoide verification page states that GetApps (Xiaomi) and OPPO App Market are Aptoide Connect partners. Selecting channels does not change any documented build requirement.

### Epic

- Status on 2026-11-17: mobile publishing is not open to all developers in the public docs. Every mobile page sits under "Mobile Early Adopter" and returns "403 - Access Denied" with a pointer to an interest form; the PC Get Started and Requirements pages tell Mobile Early Adopter members to use those gated pages. The distribution landing page offers self-service publishing for "PC games". No Epic announcement was found that mobile self-publishing opened in August 2026. Epic therefore has no public developer rules for Android builds; only store-wide rules (content, ratings, payments) and a few mobile notes are public.
- Store app: Android worldwide, downloaded directly from the Epic website (the "Epic Games app" on Google Play only covers chat and 2FA). Store app needs Android SDK 24 or later, SDK 34 or later recommended, about 25 MB. It has Epic Account login and an auto-update feature for installed games (January 2025).
- Package format (APK, AAB or split APKs), size limits, signing rules, minimum and target API for third-party Android games: not public.
- Required SDKs: none publicly mandated for mobile. Crossplay is not mandatory for mobile (iOS, Android) products; Epic Games Store achievements are not mandatory for mobile products. EOS services (Ecom, achievements, cloud saves) are listed as optional. EOS SDK for Android: AAR not hosted on Maven, API level 26 for EOS 1.19.1.2 to 1.19.2.1 (API 23 for older), arm64-v8a and x86_64 from 1.19.0.7, not thread safe, JDK 11 and R8 8.x needed.
- Payments: Epic payment keeps 100% of the first 1,000,000 USD net revenue per title per calendar year (combined across PC, Mac, iOS, iPadOS and Android, from 2025-06-01), then 88/12; third-party payments carry a 0% fee (Epic, 2025-01-24). Web Shops (Epic payment) work for mobile games on any store and are governed by Apple and Google steering rules per territory. The PC self-service flow charges a recoupable 100 USD submission fee per game; the mobile fee is not public.
- Refunds: games are generally refundable; products with virtual currency or other consumables, and most in-app purchases, are non-refundable; Epic cannot refund purchases made outside the Epic Games Store.
- Ratings: IARC certificates are issued in the Developer Portal; regional rules listed in rule 43. Since 2026-10-15 Epic also supports IGRS (Indonesia), Gmedia (Saudi Arabia), DGSC (Taiwan) and RARS (Russia). Traditional ratings must be for a supported platform, which includes Android. AO is banned.
- Review: the Epic Games Store team checks product and storefront content before launch; problems come back as "issues found"; appeals go through eoshelp.epicgames.com. Content notes are required for major updates (and all updates in South Korea).
- Agreements: Epic Games Store Distribution Agreement required; the agreement page needs sign-in. Users of the publishing tools must be 18 or older.
- Android Developer Verification: the Epic Games Store is not one of the seven stores enforcing from 2026-09-30; Google plans global enforcement for all apps on certified devices in 2027.

## Conflicts and open questions

1. Google Play vs Aptoide, Play Integrity: Aptoide requires turning off the Play Console installer check (automatic protection) for the shared package. That removes Google Play's own anti-piracy check for the Google Play build too.
2. Google Play vs Aptoide, versionCode: PSV needs the Aptoide versionCode above Google Play's. Both builds share package name and key, so a later Google Play versionCode above the Aptoide one makes Google Play auto-update replace the Aptoide build (Aptoide billing lost). The prefix scheme (1004 vs 11004) must be kept in the version numbering for all store builds that share the Google Play key.
3. One build per store vs Aptoide auto-import: a game on Google Play without IAP is imported from Google Play automatically, so Aptoide distributes the Google Play build with its Google SDKs (Play Billing, Play Games, Play review). The docs do not say whether a separate Aptoide APK can be uploaded on that path without a subscription.
4. Aptoide Connect partner channels vs Xiaomi GetApps: Aptoide's verification page names GetApps (Xiaomi) and OPPO App Market as Aptoide Connect partners; the full partner list is not published (ONE Store could not be confirmed). If the studio ships its own GetApps build, the Aptoide build (Aptoide billing, maybe another key) could reach GetApps under the same package. Deselect overlapping channels in Distribution Channels.
5. Android Developer Verification: Aptoide's page says enforcement covers Android 7 or higher; Google says Android 8 (API level 26) or higher. Google's value is used here. From 2027 the requirement applies to every non-Play store in the checklist (Huawei, Samsung, Xiaomi, RuStore, ONE Store, Amazon, Aptoide, Epic) on certified devices.
6. Aptoide billing coexistence: no Aptoide page says whether Google Play Billing may remain in the Aptoide APK or how the SDK behaves when the app was installed from another store. The migration guide removes Google Play Billing; rule 17 follows it.
7. Aptoide "Web views": listed as a rejection reason without a definition. Unclear whether an in-game web view (privacy policy, news, offerwall) counts; only whole web-view apps are assumed to be rejected.
8. Aptoide age rating and 64-bit: the Aptoide Connect docs have no age-rating questionnaire (only the target audience on the Policy Declarations card) and no 64-bit, target API (beyond 16) or 16 KB page size rule. Unknown whether Aptoide Games on Google Play (US) inherits Google Play's target API rules.
9. Aptoide Trusted badge and duplicate packages: no developer-facing rule says how Aptoide treats the same package uploaded by others or with another signature; the official terms only say "Trusted" reflects automatic anti-malware tools. Third-party sources say Aptoide compares signatures with known developer signatures.
10. Aptoide APK size: the docs now say 4 GB; older snippets of the same page said 2 GB.
11. Epic Android technical rules: package format, size limits, signing, target API, update delivery, required SDKs (EOS, Epic Account login), refund handling for third-party payments and the mobile submission fee are all behind the Mobile Early Adopter gate. Ask Epic through the program before building the Epic flavor.
12. Epic promotional content: rule 50 covers paid product placement; whether ad-network interstitials and rewarded ads count as "paid advertisements" for that declaration is not stated.
13. Epic package name and signing: not public. If the Epic build uses the Google Play package name with another key, Android refuses updates between installers; if it uses its own key, rule 58 needs a separate registration.
14. Epic Web Shops vs Google Play: linking from a Google Play build to an Epic Web Shop is governed by Google Play payment and steering rules, not by Epic (Epic says so on the Web Shop Guidelines page).
